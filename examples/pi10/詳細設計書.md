## 0. 設計上の仮定・要確認事項

基本設計書で「要確認」とされた事項に対する詳細設計側の決定。実装前にステークホルダーへ確認すること。

| No | 基本設計の記載 | 本詳細設計での扱い | 影響 |
| --- | --- | --- | --- |
| A-01 | 技術スタック未確定（§2.2） | Java 17 / Spring Boot 3.3 / Spring Data JPA / Spring Security / JWT、DB は PostgreSQL 15、フロントは Vue 3 + Vite + TypeScript + Pinia + Vue Router + axios に固定 | 全セクション |
| A-02 | 商品マスタの CRUD API・画面が未定義 | 商品マスタ登録/更新/削除（POST/PUT/DELETE `/api/products`）を **追加（仮定）**。admin 専用 | API-INV（追加）、SC（商品登録/編集画面を在庫照会画面から導線として追加） |
| A-03 | ログアウト API 未定義 | `POST /api/logout` を **追加（仮定）**（JWT はステートレス、クライアント側で破棄 + サーバ側はブラックリスト不要） | API-USR（追加） |
| A-04 | 出庫と受注確定（引き当て）の関係（§5.2 要確認） | 「入庫/出庫（REQ-INV）」と「受注確定による引き当て（REQ-ORDER）」は **別操作**。確定=在庫減、確定済みキャンセル=在庫戻し | DB / API / 単体テスト |
| A-05 | 確定済み受注キャンセルの在庫戻し入れ（§8.2 要確認） | 戻し入れを **実施** する（同一トランザクション） | API-ORD-006 / UT-ORD |
| A-06 | 受注が複数商品を許容するか（要件は単一「商品」、基本設計は order_items で 1:N） | 基本設計 §5 に従い **複数明細（1:N）を許容** | DB / API / 画面 |
| A-07 | 入出庫履歴の監査（非機能 §10） | 履歴テーブル `stock_transactions` を **追加（仮定）** | DB / API / テスト |
| A-08 | パスワード複雑度ポリシー（V-010） | 最小 8 文字 + 英字 1 文字以上 + 数字 1 文字以上 | V-010 / UT-USR |
| A-09 | 入庫/出庫の権限（§6.2 要確認） | admin のみ許可（基本設計の想定を踏襲） | 権限 / テスト |

## 1. 画面仕様

フロントは SPA（Vue 3）。全画面共通レイアウト: 上部ヘッダー（ロゴ、ログインユーザー名、ロール、ログアウトボタン）、左サイドメニュー（ロールで表示制御）、コンテンツ領域。
認証トークンは `localStorage` に保持し、axios インターセプタで `Authorization: Bearer <token>` を付与。401 受信時はログイン画面へリダイレクト（E-401）。

### 1.1 ログイン画面（SC-USR-002）

- **レイアウト**: 中央カード。ログイン ID、パスワード、ログインボタン。
- **入力項目**:

| 項目 | 型 | 必須 | 検証（対応 V-No） |
| --- | --- | --- | --- |
| ログイン ID | text | はい | 必須（V-009） |
| パスワード | password | はい | 必須（V-010） |

- **トリガーイベント**: ログインボタン押下 → `POST /api/login`。成功時トークンとユーザー情報を Pinia に保存し、在庫照会画面へ遷移。401 は「ID またはパスワードが違います」（E-401）。

### 1.2 在庫照会画面（SC-INV-001）

- **レイアウト**: 検索バー（商品名キーワード）、商品一覧テーブル、ページネーション。admin のみ「新規商品」ボタン。
- **表示項目**: ID / 名称 / 単価（¥ 整形）/ 在庫数。在庫 0 は行をグレー表示。
- **トリガーイベント**:
  - 初回表示・検索 → `GET /api/products`（`name` 部分一致）。
  - 行クリック（admin）→ 商品編集モーダル（`GET /api/products/{id}` → `PUT /api/products/{id}`）。
  - 「新規商品」（admin）→ 商品登録モーダル（`POST /api/products`）（A-02）。
- **検証（表示側）**: 入力なし。403 の場合はボタンを非表示（E-403）。

### 1.3 商品登録/編集モーダル（SC-INV-001 から導線、A-02）

| 項目 | 型 | 必須 | 検証（対応 V-No） |
| --- | --- | --- | --- |
| 商品名称 | text | はい | 必須・1〜255 文字（V-002） |
| 単価 | number | はい | 0 以上・小数 2 桁まで・最大 99,999,999.99（V-003） |
| 初期在庫数 | number | はい（登録時のみ） | 0 以上の整数（V-004） |

- **トリガー**: 保存 → `POST` / `PUT /api/products`。400 は項目単位エラーをインライン表示（E-400）。

### 1.4 入庫画面（SC-INV-002、admin 専用）

- **レイアウト**: 商品選択（検索付きドロップダウン）、入庫数量、実行ボタン、実行結果（更新後在庫数）表示。
- **入力項目**:

| 項目 | 型 | 必須 | 検証（対応 V-No） |
| --- | --- | --- | --- |
| 商品 | select | はい | 必須・存在する商品（V-001） |
| 入庫数量 | number | はい | 正の整数（1〜2,147,483,647）（V-005） |

- **トリガー**: 実行 → `POST /api/inventory/receipt`。成功時、結果カードに「前在庫 N → 現在在庫 N」を表示（REQ-INV）。

### 1.5 出庫画面（SC-INV-003、admin 専用）

- **レイアウト**: 入庫画面と同構成。商品選択時に入庫可能残数（現在在庫）を表示。
- **入力項目**: 商品（V-001）、出庫数量（正の整数、現在在庫を超えない）（V-005）。
- **トリガー**: 実行 → `POST /api/inventory/shipment`。409 は「在庫不足です（現在在庫 N）」を表示（E-409）。成功時「前在庫 N → 現在在庫 N」。

### 1.6 受注一覧画面（SC-ORD-001）

- **レイアウト**: 検索バー（顧客名・状態ドロップダウン）、受注一覧テーブル、「新規受注」ボタン。
- **表示項目**: 受注 ID / 顧客名 / 状態（DRAFT=下書き / CONFIRMED=確定 / CANCELED=取消を日本語表示）/ 明細数 / 作成日時。
- **トリガー**: 一覧取得 → `GET /api/orders`（`customerName` 部分一致、`status` 完全一致）。行クリック → 受注詳細画面へ遷移。新規受注 → 受注登録画面へ。

### 1.7 受注登録画面（SC-ORD-002、新規/更新共通）

- **レイアウト**: 顧客名入力、明細行（商品選択・数量）の追加/削除、保存ボタン。更新時は状態が DRAFT のときのみ編集可（CONFIRMED/CANCELED は読み取り専用）。
- **入力項目**:

| 項目 | 型 | 必須 | 検証（対応 V-No） |
| --- | --- | --- | --- |
| 顧客名 | text | はい | 必須・1〜255 文字（V-008） |
| 明細（1 件以上）: 商品 | select | はい | 必須・存在する商品（V-006） |
| 明細: 数量 | number | はい | 正の整数（V-007） |

- **トリガー**: 新規保存 → `POST /api/orders`（作成後 DRAFT）。更新保存 → `PUT /api/orders/{id}`。409（状態遷移不正）は「確定/取消済みの受注は編集できません」（E-409）。

### 1.8 受注詳細画面（SC-ORD-003）

- **レイアウト**: 受注ヘッダー（ID・顧客名・状態・作成日時）、明細テーブル（商品名・単価・数量・小計）、操作ボタン（状態に応じて「確定」「キャンセル」）。
- **トリガー**:
  - 初回表示 → `GET /api/orders/{id}`。
  - 確定ボタン（DRAFT のみ表示）→ 確認ダイアログ → `POST /api/orders/{id}/confirm`。成功時「確定しました（引き当て済み）」表示、状態を CONFIRMED に更新。409（在庫不足）は在庫不足メッセージを表示し状態を変更しない（E-409 / REQ-ORDER）。
  - キャンセルボタン（DRAFT/CONFIRMED で表示、CANCELED は非表示）→ `POST /api/orders/{id}/cancel`。CONFIRMED の場合「在庫を戻し入れます」と警告表示（A-05）。

### 1.9 ユーザー管理画面（SC-USR-001、admin 専用）

- **レイアウト**: ユーザー一覧テーブル、「新規ユーザー」ボタン。
- **表示項目**: ID / ログイン ID / ロール / 作成日時（パスワードは表示しない）。
- **入力項目（登録/編集モーダル）**:

| 項目 | 型 | 必須 | 検証（対応 V-No） |
| --- | --- | --- | --- |
| ログイン ID | text | はい | 必須・半角英数字・3〜32 文字・一意（V-009） |
| パスワード | password | はい（登録時）/任意（編集時） | 8 文字以上 + 英字 + 数字（V-010, A-08） |
| ロール | select | はい | `admin` / `user` のいずれか（V-011） |

- **トリガー**: 一覧 → `GET /api/users`。登録 → `POST /api/users`。編集 → `PUT /api/users/{id}`。削除 → 確認ダイアログ → `DELETE /api/users/{id}`。409（ユーザー名重複 / 最後の admin 削除禁止）はメッセージ表示（E-409）。

### 1.10 ルーティング・ガード

| パス | 画面 | 必要なロール |
| --- | --- | --- |
| `/login` | ログイン（SC-USR-002） | 未認証 |
| `/products` | 在庫照会（SC-INV-001） | admin, user |
| `/inventory/receipt` | 入庫（SC-INV-002） | admin |
| `/inventory/shipment` | 出庫（SC-INV-003） | admin |
| `/orders` | 受注一覧（SC-ORD-001） | admin, user |
| `/orders/new` | 受注登録（SC-ORD-002） | admin, user |
| `/orders/:id` | 受注詳細（SC-ORD-003） | admin, user |
| `/users` | ユーザー管理（SC-USR-001） | admin |

## 2. API 仕様

- 共通プレフィックス: なし（基本設計のパスをそのまま使用）。
- 認証: `Authorization: Bearer <JWT>`（API-USR-001 で発行）。認可は §6 権限マトリクスに準拠。
- 共通レスポンス形式（成功時は各エンドポイントの形、エラー時は共通形式）:

```json
// エラー共通形式（§8.1）
{
  "code": "E-400",
  "message": "入力値が不正です",
  "timestamp": "2025-01-01T00:00:00Z",
  "errors": [ { "field": "name", "message": "必須項目です" } ]
}
```

### 2.1 認証（REQ-USER）

#### POST /api/login（API-USR-001）

- **認証**: 不要（パブリック）。
- **リクエスト**: `{ "username": "string", "password": "string" }`
- **レスポンス 200**:
```json
{
  "token": "eyJhbGciOi...",
  "tokenType": "Bearer",
  "expiresIn": 3600,
  "user": { "id": 1, "username": "admin", "role": "admin" }
}
```
- **エラー**: 400（E-400: 必須チェック V-009/V-010）、401（E-401: ID またはパスワード不一致）。

#### POST /api/logout（A-03 追加）

- **認証**: 要（任意ロール）。
- **レスポンス 204**（サーバはステートレス、トークン破棄はクライアント側）。
- **エラー**: 401（E-401）。

### 2.2 商品（REQ-INV）

#### GET /api/products（API-INV-001）

- **認証**: admin / user。
- **クエリパラメータ**: `name`（部分一致、任意）、`page`（既定 0）、`size`（既定 20、最大 100）。
- **レスポンス 200**:
```json
{
  "items": [ { "id": 1, "name": "商品A", "price": 1000.00, "stock": 5 } ],
  "total": 1, "page": 0, "size": 20
}
```

#### GET /api/products/{id}（API-INV-002）

- **認証**: admin / user。
- **レスポンス 200**: `{ "id": 1, "name": "商品A", "price": 1000.00, "stock": 5 }`
- **エラー**: 404（E-404: 商品不存在）。

#### POST /api/products（A-02 追加）

- **認証**: admin のみ。
- **リクエスト**: `{ "name": "string", "price": 1000.00, "stock": 0 }`
- **レスポンス 201**: 作成された商品（同上形式）。
- **エラー**: 400（E-400: V-002/V-003/V-004）、403（E-403）。

#### PUT /api/products/{id}（A-02 追加）

- **認証**: admin のみ。
- **リクエスト**: `{ "name": "string", "price": 1000.00, "stock": 5 }`
- **レスポンス 200**: 更新後の商品。
- **エラー**: 400（E-400）、403（E-403）、404（E-404）。

#### DELETE /api/products/{id}（A-02 追加）

- **認証**: admin のみ。
- **レスポンス 204**。
- **エラー**: 403（E-403）、404（E-404）、409（E-409: 受注明細から参照されているため削除不可。FK 制約に基づく）。

### 2.3 在庫（REQ-INV）

#### POST /api/inventory/receipt（API-INV-003、admin）

- **リクエスト**: `{ "productId": 1, "quantity": 10 }`
- **レスポンス 200**:
```json
{ "productId": 1, "previousStock": 5, "quantity": 10, "currentStock": 15 }
```
- **エラー**: 400（E-400: V-001/V-005）、403（E-403）、404（E-404）。

#### POST /api/inventory/shipment（API-INV-004、admin）

- **リクエスト**: `{ "productId": 1, "quantity": 3 }`
- **レスポンス 200**: receipt と同形式（`currentStock` は減算後）。
- **エラー**: 400（E-400）、403（E-403）、404（E-404）、409（E-409: 在庫不足。`message` に現在在庫を含める）。

#### GET /api/inventory/transactions（A-07 追加、admin）

- **クエリパラメータ**: `productId`（任意）、`page`、`size`。
- **レスポンス 200**: `{ "items": [ { "id": 1, "productId": 1, "type": "IN", "quantity": 10, "relatedOrderId": null, "createdBy": "admin", "createdAt": "..." } ], "total": 1, "page": 0, "size": 20 }`
- **エラー**: 403（E-403）。

### 2.4 受注（REQ-ORDER）

#### GET /api/orders（API-ORD-001）

- **認証**: admin / user。
- **クエリパラメータ**: `customerName`（部分一致）、`status`（DRAFT|CONFIRMED|CANCELED）、`page`、`size`。
- **レスポンス 200**:
```json
{
  "items": [
    {
      "id": 1, "customerName": "顧客A", "status": "DRAFT",
      "itemCount": 2, "createdAt": "...",
      "items": [
        { "productId": 1, "productName": "商品A", "quantity": 3, "unitPrice": 1000.00 }
      ]
    }
  ],
  "total": 1, "page": 0, "size": 20
}
```

#### POST /api/orders（API-ORD-002）

- **認証**: admin / user。
- **リクエスト**: `{ "customerName": "顧客A", "items": [ { "productId": 1, "quantity": 3 } ] }`
- **レスポンス 201**: 作成された受注（状態 DRAFT）。
- **エラー**: 400（E-400: V-006/V-007/V-008、明細 0 件は E-400）、403（E-403）、404（E-404: 商品不存在）。

#### GET /api/orders/{id}（API-ORD-003）

- **認証**: admin / user。
- **レスポンス 200**: 受注詳細（明細含む、上記 items 展開形）。
- **エラー**: 404（E-404）。

#### PUT /api/orders/{id}（API-ORD-004）

- **認証**: admin / user。
- **リクエスト**: POST と同形式。
- **レスポンス 200**: 更新後の受注。
- **エラー**: 400（E-400）、403（E-403）、404（E-404）、409（E-409: 状態が DRAFT 以外）。

#### POST /api/orders/{id}/confirm（API-ORD-005）

- **認証**: admin / user。
- **レスポンス 200**:
```json
{ "id": 1, "status": "CONFIRMED", "allocatedStock": [ { "productId": 1, "quantity": 3, "remainingStock": 2 } ] }
```
- **処理**: 受注を CONFIRMED に遷移し、明細ごとに在庫を減算・在庫履歴（OUT、relatedOrderId 付き）を記録。商品行は `SELECT ... FOR UPDATE` でロックし、在庫不足なら全量ロールバック（E-409）。同一トランザクション（§5.2 / REQ-ORDER）。
- **エラー**: 403（E-403）、404（E-404）、409（E-409: 在庫不足、または状態が DRAFT 以外）。

#### POST /api/orders/{id}/cancel（API-ORD-006）

- **認証**: admin / user。
- **レスポンス 200**: `{ "id": 1, "status": "CANCELED" }`
- **処理**:
  - DRAFT → CANCELED: 在庫変動なし。
  - CONFIRMED → CANCELED: 明細分の在庫を戻し入れ（A-05）、在庫履歴（IN、relatedOrderId 付き）を記録。同一トランザクション。
- **エラー**: 403（E-403）、404（E-404）、409（E-409: 既に CANCELED）。

### 2.5 ユーザー（REQ-USER）

#### GET /api/users（API-USR-002、admin）

- **レスポンス 200**: `{ "items": [ { "id": 1, "username": "admin", "role": "admin", "createdAt": "..." } ], "total": 1, "page": 0, "size": 20 }`
- **エラー**: 403（E-403）。

#### POST /api/users（API-USR-003、admin）

- **リクエスト**: `{ "username": "string", "password": "string", "role": "admin" }`
- **レスポンス 201**: `{ "id": 2, "username": "user1", "role": "user" }`（パスワードは返さない）。
- **エラー**: 400（E-400: V-009/V-010/V-011）、403（E-403）、409（E-409: username 重複）。

#### PUT /api/users/{id}（API-USR-004、admin）

- **リクエスト**: `{ "password": "string", "role": "user" }`（password は任意。省略時は変更しない）。
- **レスポンス 200**: 更新後のユーザー（パスワードなし）。
- **エラー**: 400（E-400）、403（E-403）、404（E-404）、409（E-409: 最後の admin を user に変更不可）。

#### DELETE /api/users/{id}（API-USR-005、admin）

- **レスポンス 204**。
- **エラー**: 403（E-403）、404（E-404）、409（E-409: 最後の admin、または自分自身は削除不可）。

## 3. DB スキーマ

RDB は PostgreSQL 15。マイグレーションは Flyway（`src/main/resources/db/migration/V1__init.sql`）。基本設計 §5 のエンティティから導出し、`stock_transactions` を A-07 として追加する。

> 命名規則: テーブルは複数形、PK は `id BIGINT GENERATED ALWAYS AS IDENTITY`、監査列 `created_at` / `updated_at` を全テーブルに付与。

```sql
-- V1__init.sql
CREATE TABLE products (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- 基本設計: id
  name        VARCHAR(255) NOT NULL,                            -- 基本設計: name
  price       NUMERIC(10,2) NOT NULL CHECK (price >= 0),        -- 基本設計: price（単価）
  stock       INTEGER NOT NULL CHECK (stock >= 0),              -- 基本設計: stock（在庫数）
  created_at  TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
  updated_at  TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- 基本設計: id
  customer_name VARCHAR(255) NOT NULL,                           -- 基本設計: customer_name
  status        VARCHAR(20) NOT NULL DEFAULT 'DRAFT'
                CHECK (status IN ('DRAFT','CONFIRMED','CANCELED')), -- 基本設計: status
  created_at    TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
  updated_at    TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now()
);
CREATE INDEX idx_orders_status ON orders (status);
CREATE INDEX idx_orders_customer_name ON orders (customer_name);

CREATE TABLE order_items (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- 基本設計: id
  order_id   BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE, -- 基本設計: FK→orders.id
  product_id BIGINT NOT NULL REFERENCES products(id),          -- 基本設計: FK→products.id
  quantity   INTEGER NOT NULL CHECK (quantity > 0)             -- 基本設計: quantity（>0）
);
CREATE INDEX idx_order_items_order_id ON order_items (order_id);
CREATE INDEX idx_order_items_product_id ON order_items (product_id);

CREATE TABLE users (
  id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- 基本設計: id
  username      VARCHAR(255) NOT NULL UNIQUE,                    -- 基本設計: username（UNIQUE）
  password_hash VARCHAR(255) NOT NULL,                           -- 基本設計: password_hash
  role          VARCHAR(20) NOT NULL CHECK (role IN ('admin','user')), -- 基本設計: role
  created_at    TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
  updated_at    TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now()
);

-- A-07 追加: 入出庫履歴
CREATE TABLE stock_transactions (
  id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  product_id      BIGINT NOT NULL REFERENCES products(id),
  type            VARCHAR(10) NOT NULL CHECK (type IN ('IN','OUT')),
  quantity        INTEGER NOT NULL CHECK (quantity > 0),
  related_order_id BIGINT REFERENCES orders(id), -- 受注由来のみ設定
  created_by      VARCHAR(255) NOT NULL,
  created_at      TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now()
);
CREATE INDEX idx_stock_txn_product_id ON stock_transactions (product_id);
CREATE INDEX idx_stock_txn_created_at ON stock_transactions (created_at);
```

### 3.1 エンティティ ↔ テーブル対応

| 基本設計 §5 エンティティ | テーブル | 要件 |
| --- | --- | --- |
| products | products | REQ-INV |
| orders | orders | REQ-ORDER |
| order_items | order_items | REQ-ORDER |
| users | users | REQ-USER |
| （追加） | stock_transactions | REQ-INV（A-07） |

### 3.2 同時実行制御

- 受注確定（API-ORD-005）では、明細に含まれる `products` 行を **product_id 昇順で `SELECT ... FOR UPDATE`** により行ロックし、`orders` 行もロックして状態遷移の重複を防ぐ。デッドロック回避のため取得順を固定する（REQ-ORDER / §5.2 / §10 可用性）。
