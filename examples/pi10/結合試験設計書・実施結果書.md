## 1. 結合試験計画

### 1.1 試験範囲

| 項目 | 内容 |
| --- | --- |
| 対象 | バックエンド（Spring Boot 3.3）のモジュール間連携、および API 契約レベルでのフロントエンド接続性 |
| 実施レベル | **バックエンド結合（Service 間／Controller-Service-Repository-DB 間／Security-Controller 間）** |
| 非対象 | 単一 API の入出力検証（UT 担保済み）、ブラウザ E2E（実行環境にブラウザ自動化基盤が無いため後続フェーズに延期） |
| 結合観点 | (1) 認証→認可→API、(2) ユーザー管理→認証、(3) 受注→在庫→履歴、(4) トランザクション境界、(5) 権限マトリクス、(6) 共通エラー形式の横断伝播 |

### 1.2 対象モジュール間連携

```text
[認証基盤]                    [ビジネス]
AuthController                ProductController ── ProductService ── ProductRepository ─┐
  └─ AuthService ── UserRepository ── users                                            │
      └─ JwtTokenProvider ──(JWT)──▶ JwtAuthenticationFilter ──▶ SecurityConfig(認可)   │  DB
UserController ── UserService ── UserRepository ── users                                │
InventoryController ── InventoryService ── ProductRepository / StockTransactionRepository┤
OrderController ── OrderService ──┬─ OrderRepository / OrderItemRepository ─────────────┘
                                  └─ InventoryService（applyIn / applyOut を再利用）
```

| 連携境界 | 出力モジュール → 入力モジュール | 検証内容 |
| --- | --- | --- |
| B-01 認証→認可→API | AuthService（JWT 発行）→ JwtAuthenticationFilter（検証・SecurityContext 設定）→ SecurityConfig（ロール判定）→ 各 Controller | ログインで得たトークンが保護 API で使えるか |
| B-02 ユーザー管理→認証 | UserService（BCrypt 保存）→ users → AuthService（PasswordEncoder 照合）→ JwtTokenProvider | 作成したユーザーが即ログインできるか |
| B-03 受注→在庫→履歴 | OrderService（confirm/cancel）→ InventoryService（applyOut/applyIn）→ products / stock_transactions | 状態遷移・在庫減算・履歴記録が同一トランザクションで整合するか |
| B-04 トランザクション境界 | OrderService → InventoryService → GlobalExceptionHandler | 在庫不足時の全量ロールバックとエラー伝播 |
| B-05 権限マトリクス | SecurityConfig → JwtAuthenticationFilter → 各 Controller | user ロールの許可/拒否が各 API で一貫するか |
| B-06 共通エラー形式 | 各 Service の ApiException / Bean Validation → GlobalExceptionHandler → ErrorResponse | code/message/timestamp/errors が全境界で統一されるか |

| 項目 | 内容 |
| --- | --- |

| DB | H2（`MODE=PostgreSQL`）+ Flyway `V1__init.sql` 適用（`src/test/resources/application.yml`） |

## 2. 結合テストケース

> 各ケースは `given（準備）→ when（実行）→ then（期待）` 形式で、全て実 HTTP リクエスト経由。

### IT-001 認証 → 認可 → 商品照会の連携

- **ID**: IT-001
- **要件**: REQ-008 / REQ-009 / REQ-002（UT-AUTH-001 / UT-AUTH-005 / UT-PROD 系との結合確認）
- **前提条件（Precondition）**: admin が初期投入済み。商品は未登録（total=0）
- **入力（Input）**: `POST /api/login {admin/admin123}` → 得た JWT を `Authorization: Bearer` で `GET /api/products` へ付与
- **手順（Steps）**:
  1. ログイン API で admin の JWT を取得
  2. その JWT で商品一覧 API を呼び出す
- **期待結果（Expected）**: ログイン 200（token 非空）。商品一覧 200・`total=0`
- **連携境界**: AuthService（JWT 発行）→ JwtAuthenticationFilter（検証）→ SecurityConfig（認可）→ ProductController → ProductService → ProductRepository → DB
- **結果**: **PASS**

### IT-002 ユーザー管理 → 認証の連携

- **ID**: IT-002
- **要件**: REQ-007 / REQ-008（UT-USR-001 / UT-AUTH-001 の結合確認）
- **前提条件（Precondition）**: admin トークン取得済み。`integuser1` は未登録
- **入力（Input）**: `POST /api/users {integuser1 / Passw0rd1 / user}`（admin）→ その後 `POST /api/login {integuser1 / Passw0rd1}`
- **手順（Steps）**:
  1. admin でユーザー `integuser1` を作成（201）
  2. 作成直後に同じ資格情報でログインし、JWT を取得
  3. その JWT で受注一覧 API を呼び出す
- **期待結果（Expected）**: 作成 201（パスワード非公開）。ログイン 200（token 非空）。受注一覧 200
- **連携境界**: UserService（BCrypt ハッシュ保存）→ UserRepository → users → AuthService（PasswordEncoder 照合）→ JwtTokenProvider
- **結果**: **PASS**

### IT-003 受注確定 → 在庫引き当て → 履歴記録の連携

- **ID**: IT-003
- **要件**: REQ-006 / REQ-015（UT-ORD-009 / UT-INV-004 の結合確認）
- **前提条件（Precondition）**: 商品「結合商品A」（stock=10）、DRAFT 受注（数量 3）を作成済み
- **入力（Input）**: `POST /api/orders/{id}/confirm`（admin）
- **手順（Steps）**:
  1. 受注確定 API を呼び出す
  2. 商品詳細 API で在庫数を確認
  3. 在庫履歴 API で履歴を確認
- **期待結果（Expected）**: 確定 200・`status=CONFIRMED`・`remainingStock=7`。商品照会 `stock=7`。履歴に `type=OUT, quantity=3, relatedOrderId=<受注ID>`
- **連携境界**: OrderService（confirm）→ InventoryService.applyOut（行ロック済み Product 減算）→ ProductRepository / StockTransactionRepository → DB（同一トランザクション）
- **結果**: **PASS**

### IT-004 受注確定（在庫不足）の全量ロールバックとエラー伝播

- **ID**: IT-004
- **要件**: REQ-006 / REQ-014 / REQ-011（UT-ORD-010 / UT-INV-006 の結合確認）
- **前提条件（Precondition）**: 商品「結合商品B」（stock=5）、DRAFT 受注（数量 10）を作成済み
- **入力（Input）**: `POST /api/orders/{id}/confirm`（admin）
- **手順（Steps）**:
  1. 在庫不足の状態で受注確定 API を呼び出す
  2. 商品詳細・受注詳細・在庫履歴を確認
- **期待結果（Expected）**: 確定 409・`code=E-409`。商品 `stock=5`（不変）。受注 `status=DRAFT`（不変）。履歴 `total=0`（部分更新なし）
- **連携境界**: OrderService → InventoryService 減算要求 → ApiException(E-409) → GlobalExceptionHandler → ErrorResponse（トランザクション境界を跨いだ整合）
- **結果**: **PASS**

### IT-005 確定受注キャンセル → 在庫戻し入れ → 履歴記録の連携

- **要件**: REQ-005 / REQ-006 / REQ-015（UT-ORD-013 の結合確認）

- **手順（Steps）**:

- **期待結果（Expected）**: キャンセル 200・`status=CANCELED`。商品 `stock=8`（戻し入れ）。履歴に `type=IN, quantity=3, relatedOrderId=<受注ID>`
- **連携境界**: OrderService（cancel）→ InventoryService.applyIn（在庫戻し）→ StockTransactionRepository → DB
- **結果**: **PASS**

### IT-006 入出庫 → 在庫照会 → 履歴（実行者記録）の連携

- **ID**: IT-006
- **要件**: REQ-003 / REQ-004 / REQ-015（UT-INV-001 / UT-INV-004 の結合確認）

- **手順（Steps）**:
  1. 入庫（+7）→ 出庫（-2）を実行

### IT-007 権限マトリクス（認可境界）の横断検証
