## 1. システム概要

本システムは、商品の在庫管理・受注管理・ユーザー管理を提供する Web アプリケーションである。

- 商品マスタ（ID・名称・単価・在庫数）の登録・参照・更新・削除を提供する（REQ-001）
- 商品の在庫照会、および入庫（在庫加算）・出庫（在庫減算）を提供する（REQ-002 / REQ-003 / REQ-004）
- 受注（商品・数量・顧客名）の作成・参照・更新・キャンセルを提供し、受注確定時に在庫を引き当てる（REQ-005 / REQ-006）
- 管理者によるユーザー（ID・パスワード・ロール）管理を提供する。ロールは `admin` / `user` の 2 種（REQ-007）
- ID・パスワードによる認証（ログイン／ログアウト）と、ロールによる認可（アクセス制御）を提供する（REQ-008 / REQ-009）
- 入出庫・受注確定／キャンセルに伴う在庫変動の履歴を記録し、追跡・監査を可能にする（REQ-015）

システムはクライアント（ブラウザ）・アプリケーションサーバ・データベースの 3 層構成とする。

> 前提: 商品マスタ CRUD（REQ-001）、ログアウト（REQ-008）、入出庫履歴（REQ-015）は要件書 `requirements.md` に明記がないため、設計側で仮定として追加した。正式要件として含めるかは要確認。

## 2. アーキテクチャ

### 2.1 全体構成

```
[ブラウザ(SPA)] ⇔ [Webアプリケーション(REST API)] ⇔ [RDB]
```

- フロントエンド: SPA（HTML/CSS/JS）
- バックエンド: REST API サーバ
- データベース: リレーショナル DB（トランザクション対応）

### 2.2 技術選定と理由

| 領域 | 選定 | 理由 | 要件 |
| --- | --- | --- | --- |
| フロントエンド | Vue 3 + Vite + TypeScript | 画面操作を API で完結させ、ロールに応じた表示制御を実現するため（REQ-002 / REQ-009） | REQ-002 / REQ-009 |
| バックエンド | Java 17 / Spring Boot 3.3（REST API） | 画面・将来の外部連携の双方から利用可能にし、宣言的トランザクションを利用するため（REQ-005 / REQ-006） | REQ-005 / REQ-006 |
| DB | PostgreSQL 15（RDB） | 受注確定時の在庫引き当てを原子的（同一トランザクション）に処理するため（REQ-006 / REQ-014） | REQ-006 / REQ-014 |
| ORM / マイグレーション | Spring Data JPA / Flyway | スキーマ管理と SQL インジェクション対策（プリペアドステートメント）を担保するため（REQ-013） | REQ-013 |

### 5.2 ER 関係

```
users 1 ─── n（利用）
orders 1 ─── n order_items n ─── 1 products
stock_transactions n ─── 1 products
stock_transactions n ─── 0..1 orders（related_order_id、任意）
```

- 受注と商品は多対多だが、数量を持つため `order_items` を中間テーブルとして 1 対多に分解する（REQ-005）
- 受注確定時の在庫引き当ては `orders` の状態変更と `products.stock` の減算、および `stock_transactions` への記録を同一トランザクションで処理する（REQ-006 / REQ-014 / REQ-015）
- 受注確定時の同時実行は商品行ロック（`SELECT ... FOR UPDATE`）で在庫整合を保証する（REQ-006 / REQ-014）

> 要確認: 出庫（REQ-004）と受注確定による引き当て（REQ-006）が同一の在庫減算を指すのか、出庫は受注外の払い出しも許容するのかは要件に明記がない。本設計では「入出庫（REQ-003 / REQ-004）」と「受注確定による引き当て（REQ-006）」を別操作として扱う。
> 要確認: 要件書は受注の商品を単一と読めるが、本設計では複数明細（1:N）を許容する。どちらに確定するか要確認（REQ-005）。

## 8. 例外処理

### 8.1 エラーコード

| コード | 内容 | 対応 HTTP ステータス | 要件 |
| --- | --- | --- | --- |
| E-400 | 入力検証エラー（V-001〜V-011 違反） | 400 | REQ-010 |
| E-401 | 認証エラー（未ログイン・無効トークン・認証情報不一致） | 401 | REQ-008 |
| E-403 | 権限エラー（ロール不足） | 403 | REQ-009 |
| E-404 | 対象リソース不存在 | 404 | 全 REQ |
| E-409 | 在庫不足・重複・状態遷移不正 | 409 | REQ-004 / REQ-005 / REQ-006 / REQ-007 |
| E-500 | システムエラー | 500 | 全 REQ |

### 8.2 共通レスポンス形式・ハンドリング方針

- 全てのエラーは共通形式 `{ code, message, timestamp, errors[] }` で返し、クライアントが一貫して処理できるようにする（REQ-011）
- 受注確定時に在庫が不足する場合は E-409 を返し、確定を中断する。在庫減算は行わない（REQ-006）
- 確定済み受注のキャンセルでは在庫を戻し入れ、同一トランザクションで処理する（REQ-005 / REQ-006 / REQ-014）
- 認証・認可エラーはログイン画面へ誘導、または 403 を返す（REQ-008 / REQ-009）

> 要確認: 確定済み受注のキャンセル時の在庫戻し入れの有無は要件に明記がないため、戻し入れを行う想定とした（REQ-005 / REQ-006）。
