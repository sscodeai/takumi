# ADR-039: The Delivered Tests Must Be Able to Fail

- **Date**: 2026-10-06
- **Status**: Accepted. Implemented in `packages/core/src/requirement-decisions.ts` (the
  `mutation-detection` relation in `JUDGE_RELATION_VOCABULARY`, `JUDGE_MUTATION_FORMATS`,
  `MIN_MUTATION_TIMEOUT_MS`, `MutationBlock`, `parseMutation`, and the front-door refusals),
  `packages/core/src/index.ts` (the exports), `extensions/judges/metamorphic-forge.sh` (the `mutation:`
  parser, the `mutation_report_failures` reader, the `mutation-detection)` dispatch), and
  `extensions/skills/req-intake/prompts/intake.md` (rule 16, the example); tests in
  `packages/core/src/test/judge-forge-mutation.test.ts` and `packages/core/src/test/feedback-brief.test.ts`.
  The agreed design is `docs/design/mutation-relation.md`.
- **Related**: ADR-013 (the vacuous green), ADR-026 (a forged judge), ADR-028 (a decision is only real
  if it is checked), ADR-031 (a decision must say what it means to a judge), ADR-033 (the document
  declares the world its judge checks), ADR-035 (a scenario is a check the document declares)

## Context

The forged judge checks the deliverable's OUTPUT: rows reshuffled, parts summed against the whole,
repeated keys resolved, malformed rows accounted for, an independent recomputation compared, and (since
ADR-035) a page or a service answering a command the document declares. Every one of those checks runs
the DELIVERABLE and inspects what it printed.

The vacuous-green guard (ADR-013, hardened by ADR-033) catches the case where the deliverable's output
matches NO declared shape: when nothing the tool printed can be parsed through a declared output shape,
no relation may pass, because both sides of every comparison would be empty. That guard is real, and it
fixed bug ledger #37.

It does not catch the more common failure. **The deliverable ran, it printed something the shapes can
parse, the relations agreed — and the implementation was wrong in a way the checks happened not to
exercise.** Worse, and this is the case this ADR is about: the implementation's OWN test suite may be
green while asserting nothing that a wrong implementation would contradict. A suite that only asserts
"the command exits 0", or "the file exists", or "the line count is positive" is green on a wrong
implementation, and no output-shape check can tell, because the output is well-formed.

That suite is the deliverable's own claim about itself. Nothing in the six existing relations can test
it, because they read the output, not the tests.

## Decision

A document may declare a `mutation-detection` relation, and a `mutation:` block that CONFIGURES it. The
block is not itself a check — it is the tool configuration the relation runs.

```yaml
deliverable:
  relations:
    - id: REL-005
      relation: mutation-detection
      decides: AMB-00n          # optional, as for every other relation
      description: "The delivered tests fail when the delivered behaviour is mutated."
  mutation:
    run: "npx stryker run --reporters json"        # required: how the judge runs the tool, in the worktree
    report_path: "reports/mutation/mutation.json"  # required: where the tool writes its verdict
    format: survivors-json                          # required; the design's first, tool-agnostic reader
    max_survivors: 0                                # required: how many uncaught mutants are tolerated
    timeoutMs: 900000                               # optional; a mutation run is many test runs
```

1. **The judge runs the delivered project's own tooling against the delivered project's own tests.** It
   executes `mutation.run` in the delivery worktree with the declared timeout, and reads the report the
   document points at. The mutants are generated by the TOOL, from the code that exists — not by the
   implementer — which is what makes this an expectation the implementation cannot supply. This is the
   property that puts the check in the third ring (ADR-026) rather than being one more thing the
   implementer grades itself on.

2. **`survivors-json` is deliberately first and deliberately boring.** A tool-agnostic report
   `{"total": <int>, "survivors": [{"file": "…", "line": 12, "description": "…"}, …]}` lets the relation
   be proven end to end before any specific tool's schema is wired in. It is read by a small STRICT JSON
   reader in the judge (awk only, so the judge stays a shell script): it accepts exactly those top-level
   keys and exactly those survivor keys, and refuses anything else. A format the judge does not implement
   is refused, not guessed.

3. **The report decides, not the exit code.** A mutation tool legitimately exits non-zero when mutants
   survive, so a non-zero exit is not by itself a failure. But a command that did not run at all is:
   exit 127 (the binary is missing) and exit 124 (the run outlived `timeoutMs`) fail closed, naming the
   command and saying the tests were never exercised.

4. **Every path where the tool did not actually run fails CLOSED.** Missing report, unparseable report, a
   report with a key outside the declared shape, and `total: 0` all fail, naming the path and what the
   judge could not read. `total: 0` is a failure on purpose: a run that measured no mutants cannot fail
   a test, so it is not a pass. This is the vacuous green one level up — a mutation check that could not
   run reported as green — and the relation exists to make it impossible.

5. **`survivors <= max_survivors` → `ok`; otherwise `not ok`, naming the survivors.** The `not ok` line
   names the count, the budget and the measured total, and lists the surviving mutants (file, line,
   description). A decision bound to the relation reports NOT honoured through the existing `DEC-nnn`
   mechanism, exactly as a relation that fails does.

6. **The front door refuses what cannot be judged** (before a human confirms, and again in the forge): a
   `mutation-detection` relation with no `mutation:` block; a `mutation:` block with no relation using it;
   more than one mutation relation (one block configures one check); a block with no `run`, no
   `report_path`, an unknown `format`, a `max_survivors` that is not a non-negative integer, or a
   `timeoutMs` below the honest floor. `MIN_MUTATION_TIMEOUT_MS = 5000` is a FLOOR, not a
   recommendation: a mutation tool runs the delivered suite once per mutant, so a bound below five
   seconds cannot honestly contain even a two-mutant pass. The design's example declares 900000.

## What this catches, and what it does not

**It catches a delivered suite that cannot detect deliberately introduced faults.** The judge injects
small defects into the delivered source and requires the delivered TESTS to fail on them; the mutants a
suite lets survive are, by construction, behaviours it does not assert. This is the failure the
vacuous-green guard cannot see: the deliverable's output is well-formed and the output-shape relations
are satisfied, but the suite that is supposed to protect the behaviour is inert.

**It does NOT catch a suite that only asserts trivialities, if those trivialities happen to kill
mutants.** A mutation tool changes the code and sees whether the suite notices; a test that asserts
`exit == 0` will kill a mutant that makes the program crash, and an assertion that a file is non-empty
will kill a mutant that empties it. Killing a mutant proves the test is sensitive to SOME change, not
that it asserts the behaviour the human chose. Mutation score is not correctness: a high score says the
tests CAN fail; it says nothing about whether the behaviour is the one that was agreed.

**So this relation is COMPLEMENTARY to the six existing ones, not a replacement.** The six check the
deliverable's output against the document's declared world; this one checks the deliverable's own suite
against deliberately broken versions of its own source. A document that declares this relation and drops
the others has traded output correctness for test sensitivity, which is a strictly worse trade. It sits
BESIDE the relations.

**It measures the DELIVERED project's tests, run by the delivered project's own tooling.** It is not a
judge-side mutation of a judge-side fixture. The tool, the test runner and the language are the
deliverer's; the judge only starts the command and reads the report. That is what makes it evidence
about the delivery rather than about the judge — and it is also why the judge fails closed when the tool
is missing rather than installing anything: a network fetch inside an acceptance step is not something a
judge should do, and tool install is the operator's job.

## Evidence

`packages/core/src/test/judge-forge-mutation.test.ts` (8 tests) runs the REAL forge and the REAL judge
against a real fixture project whose `mutation:` block names a real script that writes a real report.
Every test asserts on the judge's WORDING, not merely its exit code:

- a run within the declared budget → `ok N - REL-001 mutation-detection: the delivered tests fail when
  the delivered behaviour is mutated (0 survivor(s) tolerated)`;
- survivors over the budget → `not ok … — 2 survivor(s) over the budget of 0 (of 5 mutant(s) measured):
  src/sum.sh:12 (removed the mean); src/sum.sh:20 (replaced + with -);`;
- a command that does not exist → `not ok … — the mutation command could not run (exit 127), so the tests
  were never exercised: this-tool-does-not-exist --run`;
- a command that outlives `timeoutMs` → `not ok … — the mutation command timed out after 5000ms, so the
  tests were never exercised: sleep 60`;
- a missing report → `not ok … — the report …/e2e/mutation.json does not exist (the command exited 0): a
  mutation run whose report the judge cannot read is not a pass`;
- a malformed report → `not ok … — the report … is not the declared survivors-json shape: the report is
  not a JSON object`;
- a report with an unknown key → `not ok … — the report declares the key "killed" where the declared
  shape has only total and survivors`;
- zero mutants measured → `not ok … — the report … measured 0 mutant(s): a mutation run that measured
  nothing cannot fail a test, so it is not a pass`.

`packages/core/src/test/feedback-brief.test.ts` (`validate: the mutation block is checked before a human
confirms it (ADR-039)`) asserts each front-door refusal, and that a well-formed block with its relation
is not refused. The relation joins the vocabulary test
(`packages/core/src/test/judge-vocabulary.test.ts`), which compares `JUDGE_RELATION_VOCABULARY` against
the forge's `IMPLEMENTED` list so the two cannot drift.

## Honest limits

- **Cost.** A mutation run executes the delivered suite once per mutant. It is the most expensive check
  in the vocabulary by an order of magnitude, which is why `timeoutMs` and `max_survivors` are declared
  rather than assumed, and why a document OPTS INTO it.
- **Per-language tooling.** There is no universal mutation tool (Stryker for JS/TS, mutmut for Python,
  cargo-mutants for Rust, PIT for the JVM). The judge reads a report; the document says which tool wrote
  it. Only `survivors-json` is implemented today — the tool-specific readers come after — and an
  unimplemented format is refused, not guessed.
- **Tool install is the operator's job.** The judge never installs anything and fails closed when the
  tool is missing.
- **The budget is a policy, not a truth.** `max_survivors: 0` is the usual choice, but a document may
  tolerate some survivors; the relation checks the number against the declared budget, not against a
  universal standard.
- **A survivor is named, not explained.** The report says which mutant lived; deciding whether the suite
  SHOULD have killed it is a human's reading of the mutant, which the judge does not attempt.

## Consequences

- The third ring gains its missing half: a delivery can now be judged on whether its own tests can fail,
  not only on whether its output is well-formed.
- The relation is the most expensive in the vocabulary and the only one that runs the deliverer's own
  test runner, so it is opt-in, bounded, and reported with the mutants it injected and the ones that
  survived.
- A report the judge cannot read is never a pass, at every level: the front door refuses a block it
  cannot configure, and the judge fails closed on a report it cannot parse, on a tool that did not run,
  and on a run that measured nothing.
