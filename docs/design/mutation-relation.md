# Mutation detection: the delivered tests must be able to fail (design)

Status: agreed with the operator (all three integration seams approved); implementation follows the
`browser-scenario` relation, which edits the same vocabulary and forge files.

## Why this is the third ring's missing half

The vacuous-green guard (ADR-033) catches the case where the deliverable's output matches no declared
shape, so no relation can be judged at all. It cannot catch the much more common case: **the deliverable
ran, the tests passed, and the tests would have passed for a wrong implementation too.** Both the
implementer's suite and, in principle, a judge whose fixtures are too kind can be green on nothing.

Mutation detection closes that: the judge injects small defects into the delivered source and requires the
delivered TESTS to fail on them. This is an expectation the implementation cannot supply — the mutants are
generated by the tool, from the code that exists — which is what makes it fit the third ring rather than
being one more thing the implementer grades itself on.

## Declaration

A relation and a block, both inside `deliverable`:

```yaml
  relations:
    - id: REL-005
      relation: mutation-detection
      decides: AMB-00n          # optional, as for every other relation
      description: "The delivered tests fail when the delivered behaviour is mutated."
  mutation:
    run: "npx stryker run --reporters json"     # required: how the judge runs the tool, in the worktree
    report_path: "reports/mutation/mutation.json"   # required: where the tool writes its verdict
    format: survivors-json | stryker | mutmut | cargo-mutants   # required
    max_survivors: 0            # required: how many uncaught mutants are tolerated (usually 0)
    timeoutMs: 900000           # optional; a mutation run is many test runs
```

`survivors-json` is deliberately first and deliberately boring: a tool-agnostic report
`{"total": <int>, "survivors": [{"file": "…", "line": 12, "description": "…"}, …]}`, which lets the
relation be proven end to end before any specific tool's schema is wired in. The tool-specific readers
come after.

## Verdict, fail-closed

1. Run `mutation.run` in the delivery worktree with the declared timeout.
2. A non-zero exit is not automatically a failure (mutation tools exit non-zero when mutants survive), so
   the report is what decides — but a command that did not run at all (missing binary, exit 127) is
   `not ok` naming the reason and the command.
3. Read `report_path` in the declared `format`. Missing file, unparseable file, zero mutants measured, or
   a format the judge does not implement → `not ok`, naming the path and what it could not read. **A
   mutation check that could not run is never a pass** — that would be the vacuous green one level up.
4. `survivors <= max_survivors` → `ok`. Otherwise `not ok` naming the survivors (file, line, description
   for `survivors-json`; the tool's own identifiers otherwise), and a decision bound to the relation
   reports NOT honoured through the existing `DEC-nnn` mechanism.
5. The scenario-style discipline applies: the judge starts nothing it does not kill, it never reads the
   implementation to decide (only to hand the tool its input), and it reports the mutants it injected and
   the ones that survived, not just a count.

## Refusals at the front door (validator, before a human confirms)

- a `mutation-detection` relation with no `mutation:` block (a check with nothing to run is not a check);
- a `mutation:` block with no `run`, no `report_path`, an unknown `format`, `max_survivors` that is not a
  non-negative integer, or a `timeoutMs` below the honest floor for a tool that runs the suite N times;
- a `mutation:` block declared with no relation using it (a tool nobody checks with is cost with no check);
- the same `decides:` / `checkedAs` rules every other relation already obeys.

## Tests

- forge + judge against a project whose tests genuinely fail on the injected mutants → `ok`,
  `ACCEPT_VERDICT: pass`.
- against a project with a vacuous suite (tests that assert nothing) → `not ok` naming a survivor, and the
  bound decision reports NOT honoured.
- a report path that does not exist, an unparseable report, and `total: 0` → `not ok` each with its reason.
- a `mutation.run` whose binary does not exist (exit 127) → `not ok`, naming the command.
- the process/timeout discipline: a mutation run that outlives `timeoutMs` is killed and fails closed.

## Honest limits

- **Cost**: mutation runs the delivered suite once per mutant. It is the most expensive check in the
  vocabulary by an order of magnitude, which is why `timeoutMs` and `max_survivors` are declared rather
  than assumed, and why it is a relation a document opts into.
- **Per-language tooling**: there is no universal mutation tool (Stryker for JS/TS, mutmut for Python,
  cargo-mutants for Rust, PIT for the JVM). The judge reads a report; the document says which tool wrote
  it. An unimplemented format is refused, not guessed.
- **Tool install is the operator's job**: the judge fails closed when the tool is missing — it never
  installs anything, and a network fetch inside an acceptance step is not something a judge should do.
- **Mutation score is not correctness**: a high score says the tests can fail; it says nothing about
  whether the behaviour is the one the human chose. It sits beside the relations, never instead of them.
