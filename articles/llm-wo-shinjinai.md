# LLM の「できました」を信じない

「実装完了しました。テストも全部通ってます」

生成AIコーディングエージェントに言われて、そのままマージしたことはないだろうか。**僕は信じないことにした。** そして「なぜ信じてはいけないのか」を数値で確かめるために、エージェント評価基盤を自作した。

この記事はその記録だ。23 タスク × 3 モデルの実測と、**評価基盤自身が自分のバグを 2 回見つけた**話まで含めて、LLM エージェントの「正しい測り方」を共有する。

## 結論（先に）

1. **明確な仕様 + 検証可能な小タスクでは、現代のエージェントは驚くほど信頼できる**（23/23 が初回合格、虚偽完了 0%）
2. **「できました」が嘘になるのは、エージェントが自己検証できないとき**（曖昧な仕様・暗黙の制約・巨大な変更）
3. **それでも独立検証レイヤーは必要**——エージェントが失敗したとき、検証がフィードバックになり修正ループで救える（実証済み）
4. **評価ツールは先に自分を検証しろ**——今回、評価スクリプトのバグが「虚偽完了 100%」という偽の結果を 2 回出した

## 背景：なぜ「信じない」のか

生成AIコーディングは「提案」であり、**検証は別レイヤーの仕事**だ。

- エージェントは自分が書いたテストで自分を確認する（自己検証 = 甘い）
- 本当の受入基準は独立した Ground Truth（隠しテスト）であるべき
- 日本の SI 開発では「エビデンス」「トレーサビリティ」が契約上の要求——「AI が言ったから OK」は通らない

この考え方を **"Agents propose. Takumi verifies."** と表現している。

## 作ったもの：エージェント評価基盤

23 個の実 SWE タスクを 6 グループ用意した：

| グループ | 内容 |
|---|---|
| easy (6) | 小バグ修正・機能追加・リグレッション |
| hard (4) | 連鎖バグ・隠れエッジ・複数ファイル |
| trap (3) | 曖昧仕様・誤解しやすい要件 |
| no-self-test (3) | **テストを実行できない環境**（自己検証不可能）|
| complex (5) | 日本語要件・在庫/カート/移行/並列/検索 |
| implicit (2) | **明言されていない暗黙の制約** |

全タスクに **隠しテスト（Ground Truth）** を用意。エージェントには見えない。評価時に注入して独立検証する。

メトリクスは厳密に定義：

- **First-pass Rate**: 初回独立検証で合格 / 全タスク
- **Claimed Rate**: エージェントが「成功」と主張 / 全タスク
- **False Completion Rate**: （成功主張かつ検証失敗）/ 成功主張
- **Repair Success Rate**: 検証失敗後に修正ループで合格 / 修正ループに入った数

## 実測結果（DeepSeek + Pi）

| ハーネス | First-pass | False Completion | 平均レイテンシ |
|---|---|---|---|
| DeepSeek v4-flash | **23/23 (100%)** | **0/23 (0%)** | 26.4s |
| Pi (opencode-zen) | 6/6 (100%) | 0/6 | 50.1s |
| DeepSeek v4-pro (complex のみ) | 4/5 (80%) | 0/4 | 74.5s |

**明確に仕様が書かれた検証可能なタスクでは、どのモデルもほぼ 100% 初回合格だった。**

これは「エージェントは信用できる」という意味ではない。**「検証可能な環境ではエージェントも自己検証できるから、ズレが表面化しない」**という意味だ。本当の危険は、エージェントが自己検証できない状況で発生する。

## 評価基盤が自分のバグを 2 回見つけた

ここが一番面白い。**評価スクリプトのバグが「虚偽完了 100%」という偽結果を 2 回出した。**

### バグ 1: 出力の期待値が実フォーマットと不一致

`node --test` の出力は `# pass 4`。なのに評価スクリプトは `"passing"` という文字列を探していた。当然マッチせず、**全タスク失敗判定** → 虚偽完了 100% という誤報。

### バグ 2: import パスの階層ミス

複数ファイルのフィクスチャで、隠しテストの import パスが `../../src/...` になっていて、ワークディレクトリの階層とズレていた。**モジュール解決エラーで全タスク失敗** → また虚偽完了 100%。

両方とも「エージェントが悪い」ように見える結果だった。**実際は測定系が悪かった。**

## 教訓：評価ツールは先に自分を検証せよ

```
1. 評価スクリプトがバグっていないか → 先に自分を検証
2. Ground Truth が本当に「正解実装なら通る」「バグ実装なら落ちる」か → 全 23 件で検証済み
3. それからエージェントを測る
```

これはエージェント評価に限らない。**AI システムの評価・テストは、測定系の信頼性がすべて**。測定系が壊れていれば、「AI がダメ」という結論も「AI が完璧」という結論も両方嘘になりうる。

## Repair Loop：検証がエージェントを救う

### ケーススタディ：実際に起きた Repair（v4-pro）

評価中に**自然発生**した失敗がある（人工注入ではなく）：

```
[ts-complex-concurrency-001] 並行キューの順序保持タスク
[1] ACT: エージェント「修正完了です」と主張
[2] VERIFY: 独立検証 FAIL ← 隠しテストが順序バグを捕捉
[3] FEEDBACK: 検証出力をエージェントに提示
[4] REPAIR: エージェントが修正
[5] RE-VERIFY: PASS ✓（修正 1 回で合格）
```

このタスクの結果（同じ評価基盤、モデルを環境変数で切り替え）：

| モデル | First-pass | Repair 発生 | 最終合格 |
|---|---|---|---|
| v4-flash | 100% (5/5) | 0 | 100% |
| **v4-pro** | **80% (4/5)** | **1 回（自然発生）** | **100% (5/5)** |

**面白いのは、強いモデル（v4-pro）の方がこのタスクで初回失敗したこと。**
モデルの強さとタスク難度の関係は単調ではない。だからこそ**検証レイヤーが全モデル共通で必要**なのだ。

これが "Agents propose. Takumi verifies." の実体だ。**エージェントの主張は提案であり、検証レイヤーが品質を保証する。**

## 次のステップ：Manage-Execute-Audit ループ

実は、この「検証が品質を保証する」考え方を**ループに拡張**したのが、最近の研究の流れだ。

**[LongHorizon-Harness](https://arxiv.org/abs/2608.01964)（arXiv 2608.01964, Alibaba DreamX）** は MEA Loop を提唱した：

- **Manager**: タスク状態を明示的に保持し、次のサブタスクを決定（環境には触れない）
- **Executor**: フレッシュコンテキストで契約を実行（唯一の書き込み者）
- **Auditor**: 読み取り専用で環境を独立検証（executor の主張だけでは状態は変わらない）

これはまさに本記事の「検証レイヤーが品質を保証する」を**長期タスクに一般化**したものだ。
**Takumi でも同じ MEA ループを実装した**（`takumi loop`）：

```
[1] MANAGE: LLM がタスク状態から次の契約を決定（DONE/BLOCKED も判定）
[2] EXECUTE: フレッシュコンテキストの LLM がワークスペースを変更
[3] AUDIT: LLM + npm test で読み取り専用検証（VERDICT: PASS/FAIL）
[4] 状態更新: クリーンな audit エビデンスがあるレコードのみ completed に
[5] 未解決なら次のラウンドへ（max-rounds で保護）
```

実際の実行例（even タスク、DeepSeek v4-flash）：
```
=== Loop finished: done after 1 round(s) ===
note: Requirement r1 ... completed with clean audit evidence — PASS verdict and npm test exit 0.
[completed] requirement r1: ... evidence: VERDICT: PASS — sumEven now sums only evens
```

**1 ラウンドで完了**。エージェントが失敗すれば、audit が FAIL を返し、次のラウンドで修正する。これが
"Agents propose. Takumi verifies." のループ版だ。

## 正直な限界

- **サンプル 23 件は小さい**（preliminary 扱い）
- **実世界の虚偽完了**（矛盾する要件・組織間・環境差異）は、この規模のタスクでは再現できない
- トークン/コスト計測は未対応
- LLM ジャッジなし（全て決定論的検証）

## まとめ

1. 検証可能なタスクならエージェントは信頼できるが、**検証レイヤーは保険として常に必要**
2. エージェント評価で最も重要なのは、**測定系の正しさ**
3. 評価基盤は自分自身のバグを見つける——それが正しく動いている証拠
4. **モデルを切り替えても同じ評価が回せる**（モデル非依存）——実際に v4-pro で自然発生した失敗を検証+修復ループが救った
5. モデルの強さとタスク難度の関係は単調ではない——**どのモデルでも検証は必要**

「できました」を信じる前に、**あなたの検証は正しいですか？**
